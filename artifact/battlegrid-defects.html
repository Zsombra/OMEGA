One pattern behind five of them

With one exception, every finding here is the same shape: the declared contract and the runtime disagree. The tool schema says a field is required and the validator refuses it. The metric contract says a transform is legal and the renderer crashes on it. The column publishes a vocabulary and then emits different words.

The two findings added on 2026-08-25 are the same shape again. The condition engine's own boilerplate names three outcomes and the engine delivers two (BG-6). A section named for the higher timeframe delivers no higher-timeframe signal (BG-7).

This is not new. Grid-Commander logged the identical class on 2026-08-15 — regimeAutoDerive and regimeTimeframe were declared required on the UPDATE plan and rejected by the live validator; dropping them made the write succeed. Six instances in eleven days suggests the contract and the executing code are not generated from one source, and that a conformance check between them would catch this class before a caller does.

Findings

BG-1Blocking

The apply schema requires a key its validator rejects

apply_strategy_plan publishes request: { plan, planToken, confirm } with all three required. Sending exactly that is refused. No accompanying "missing key" error appears, which pins the validator's accepted set to exactly {confirm, planToken}.

Schema declares
required: ["plan", "planToken", "confirm"]
Validator returns
unrecognized_keys: ['plan'] at path: ['request']
Workaround — verified three times

Omit plan entirely. The post-state is already sealed in the signed token as postStateDigest, so the client copy is redundant on the wire. 

apply_strategy_plan({ request: { confirm: true, planToken: "<verbatim>" } })

Confirmed on the REPORT axis, on CONDITIONS/MARKET_READ, and on a from-scratch CREATE. Not a quirk of one code path.

Suggested fix: the schema is the stale half — it still describes a projection the server no longer consumes. Either drop plan from the published schema, or accept and ignore it. Right now the documented call is the one that fails.

BG-2Silent

Two zone columns cannot carry a condition at all

All five classifyZone columns declare the same conditionVocabulary. Two of them never emit any of it. Measured across 12 coins:

conditionVocabulary declares
ADX_zone overbought | oversold | neutral MFI14_zone overbought | oversold | neutral
Column actually emits
ADX_zone trending | developing | weak MFI14_zone bearish | bullish in vocabulary: 0 of 12

So ADX_zone is "neutral" — written from the vocabulary the platform publishes, using the operator it lists — reads FALSE forever. Not an error. Not UNRESOLVED, which would at least signal a missing input. It looks like a working condition that happens never to fire.

And the obvious repair is refused:

CONDITION_LITERAL_UNSUPPORTED
'trending' is not a value 'ADX_zone' can take — its vocabulary is
overbought | oversold | neutral.   Nearest canonical key: 'oversold'
No workaround for the column

Both directions are closed: every label that would fire is rejected at validation, every label accepted reads FALSE. ADX_zone and MFI14_zone are display-only — renderable for an agent to read, impossible to condition on.

Replacement — reproduces the zone exactly
ADX_zone   is "weak"      →  ADX    lt  20
ADX_zone   is "trending"  →  ADX    gte 25
MFI14_zone is "bearish"   →  MFI14  lt  50
MFI14_zone is "bullish"   →  MFI14  gte 50

Verified on BTC / SOL / XRP — three for three on both columns. Those cutoffs are consistent with observation, not extracted: the zone thresholds are published nowhere.

Suggested fix: the two columns look like they were wired to a different classifier than the one their contract describes — ADX to a trend-strength bucket and MFI14 to a directional one, while both still advertise the oscillator vocabulary RSI14_zone uses correctly. Publishing the real labels would make both usable immediately. Publishing the threshold values too would remove the guesswork above.

BG-3Blocking

Crowd ranks compile cleanly and never render

Every crowd metric declares transforms: ["rank", "value"]. get_strategy_column_contract returns a complete contract for the rank — header, formula, glossary, null behaviour. Then every render fails.

Compile returns
header: crowdAcc_rank_hi formula: ordinal(crowdAcc among the ranked universe, by ordering)
Render returns
INTERNAL_ERROR Internal server error

Ruled out, each with a live probe:

  • Not the single-coin case — fails identically at 1 coin and at 10.
  • Not null data — every coin in the 10-coin set had complete crowd values.
  • Not ordering — hi and lo both fail.
  • Not a subset — all 8 crowd rank shapes fail, settled and _LIVE alike.

The contract text points at the cause. Crowd ranks are the only ones documented as "ordinal across THIS REPORT's coins … computed per request"; every other rank reads the tracked universe. That per-request path is what breaks.

Replacement

Use CROWD_* × value and threshold it. Crowd metrics are already cross-coin-comparable percentages, so unlike VOLUME they need no normalising — ranking adds nothing a threshold cannot express. 

crowdAcc between 60 and 100
  →  UP on SOL (88.9) and XRP (100.0), NEITHER on BTC (40.0)

Suggested fix: either repair the per-request ranking path, or drop rank from the crowd metrics' declared transforms so the authoring surface stops offering 8 shapes that cannot be delivered.

BG-4Friction

Trajectory direction is computed on values the table hides

A trajectory column emits its slots at the metric's display precision, but _trend is derived from the unrounded series. The two can disagree, and the table gives no way to tell. DOGE at 1h:

Slots imply
RSI14_t2 38.3 RSI14_now 38.3 → flat
Column reports
RSI14_trend falling

The platform is right — RSI displays at precision: 1 and the true endpoints differ below it. But a reader reconciling the row sees a contradiction, and anyone recomputing a direction from the rendered slots gets it wrong at exactly the close calls that matter.

Workaround

Read _trend directly; never reconstruct a direction from the slots. Worth stating in the column's own meaning text, since the trap is invisible from the output.

BG-5Friction

INTERNAL_ERROR covers transient states and real faults alike

The same opaque error is returned for a genuinely impossible shape (BG-3, which never succeeds) and for a transient condition that clears on its own. That ambiguity cost about seven hours.

The correct apply shape was found at 18:00 and refused four times with INTERNAL_ERROR. It succeeded unchanged at 19:07. The 18:40 and 19:06 requests were byte-identical — same operation, same expectedRevision, same coins, same columns — and both tokens were seconds old. Nothing client-side differed.

Separately, the connector returned 503 on every endpoint for several minutes, and two CREATE applies timed out before the third succeeded.

Workaround

On INTERNAL_ERROR, change nothing and resend the identical request. On an ambiguous timeout during CREATE, do not retry blind — the strategyId is pre-allocated inside the signed token, so reading that id settles what happened before a retry can duplicate.

Suggested fix: distinguish retryable from terminal. A typed UNAVAILABLE or RETRY_LATER would have collapsed those seven hours to one retry, and would separate BG-3 — which is permanent — from noise.

BG-6Silent

A null column value reads FALSE, never UNRESOLVED

The condition engine documents three outcomes, and its own boilerplate is explicit about what the third one means:

“TRUE / FALSE / UNRESOLVED are three distinct states; UNRESOLVED means an input was missing, not that the read was false.”

Null column data does not reach that third state. crowdAccLive rendered —, and crowdAccLive gt 50 returned FALSE, with the evidence line carrying operand: "—". unresolvedCount stayed at 0 throughout. The connective table that follows is plain two-valued logic:

expressionmembersresult
ALLTRUE, nullFALSE
ANYTRUE, nullTRUE
ANYFALSE, nullFALSE
NOTnullTRUE
N_OF n=1TRUE, FALSE, nullTRUE, unresolvedCount: 0

The cost is that “not measured” is indistinguishable from “measured and false”. crowdAccLive is null whenever no concurrent sessions are running, which is most of the time — so a condition on it reads FALSE almost always, and reads it for the wrong reason. NOT is the sharp edge: NOT(null) returns TRUE, so a negated guard fires precisely when there is no data to justify it.

Workaround

Pair any condition on a nullable column with an ALL guard on a column that is never null, so the absence of data cannot be read as a positive. Never put a nullable column under NOT.

Suggested fix: route null operands to UNRESOLVED and count them in unresolvedCount — which is what the boilerplate already promises. If two-valued logic is the intended behaviour, the boilerplate should say so, because an author reading it today will design around a state that never occurs.

BG-7Silent

includeHigherTimeframe feeds no htf_* signal

All 25 platform sections were probed individually with derive_strategy_rule_view. Seventeen feed exactly one signal module each; eight feed nothing. The mapping is otherwise perfectly regular — but one of the eight is named for the thing it does not do.

reporthtf_rsi_oversold
includeHigherTimeframe aloneNOT_IN_REPORT
includeRsi aloneIN_REPORT, reportDefaultAllocation: 1

The six rung signals — htf_rsi_*, htf_ma_*, htf_trend_adx_* — arrive with the base modules. A single RSI14 column at rel: anchor, with no regime column anywhere in the report, puts htf_rsi_oversold and ltf_rsi_oversold in report. So the section that names the higher timeframe is the one section that cannot deliver it.

An author who wants higher-timeframe confirmation reaches for the obviously-named section, allocates 3 to htf_rsi_oversold, and has weighted a signal that never fires. Nothing in the response says so: NOT_IN_REPORT is reported without a cause and without a remedy.

Workaround

Enable the base section — includeRsi, includeMovingAverages, includeTrendStrength — or add one of its metrics as a column. The rung variants come free either way.

Suggested fix: have derive_strategy_rule_view return, for every NOT_IN_REPORT rule, the sections and metrics that would feed it. The server already knows the mapping — it is what produced these 25 answers. Returning it would close this finding and remove the need for any caller to rebuild the map by probing.

What held up

A defect list is not a verdict on the product, so for balance: the authoring surface is in good shape. Everything below was exercised against the live compiler and passed.

Header contract 300 of 300 legal column shapes produced exactly the headers their contract predicted. 536 headers, zero mismatches.
Condition grammar All 7 clause operators, all 4 group operators, conditionRef, a group referencing groups, required, and verdict resolution.
Provisional flag Correct throughout — true on every condition reading a custom column, false on the one reading an ambient header.
Legality model The engine correctly refused BB_PCT_B × classifyZone as non-composable, and named the allowed transforms in the error.
Write path All seven axes commit — IDENTITY, TIMEFRAME_PROFILE, REPORT, MARKET_READ, CONDITIONS, SETUP_GATES, LIFECYCLE.
Error quality Validation errors are genuinely good — they name the key, the allowed domain, and the nearest valid value. BG-5 is the exception, not the rule.
Section membership Regular, not ad hoc. 17 of 25 platform sections feed exactly one module each, with no overlap, and every one delivers its module's full signal set — rung variants included. A section and its metric are interchangeable: includeRsi and one RSI14 column produce byte-identical membership.

How this was tested

Every column shape the metric contract declares legal was enumerated offline, batched under the measured sectionColumns cap, and rendered live — 15 batches, 300 shapes, one coin per batch for the header comparison and multi-coin renders for value checks. The condition grammar was exercised in a single report carrying every construct at once. Findings were then written to a sandbox strategy and read back to confirm persistence. Signal membership was measured separately on 2026-08-25: each of the 25 platform sections submitted alone to derive_strategy_rule_view and its IN_REPORT set recorded. The four sections in the final probe were measured jointly — membership is a union, so an empty union proves each member individually empty.

One incidental note for the budget model: columnLookback reported exactly 24 in all 13 renders — 1 through 30 columns, every transform, SMA200 included. It never moved, so it carries no information for a caller sizing a report. The cap that actually binds is sectionColumns.
