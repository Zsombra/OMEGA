One pattern behind eight of them

With one exception, every finding here is the same shape: the declared contract and the runtime disagree. The tool schema says a field is required and the validator refuses it. The metric contract says a transform is legal and the renderer crashes on it. The column publishes a vocabulary and then emits different words.

The two findings added on 2026-08-25 are the same shape again. The condition engine's own boilerplate names three outcomes and the engine delivers two (BG-6). A section named for the higher timeframe delivers no higher-timeframe signal (BG-7). BG-14, added 2026-08-28, repeats it once more: the compile tool's description pins its 256,000-byte cap to the serialized plan, and the runtime enforces it against the compile's own preview render.

This is not new. Grid-Commander logged the identical class on 2026-08-15 — regimeAutoDerive and regimeTimeframe were declared required on the UPDATE plan and rejected by the live validator; dropping them made the write succeed. BG-9 is the same shape once more, and the most mechanical yet: the transform catalogue publishes a formula for nearestZoneDist that the engine does not implement — the sign is inverted. Seven instances in eleven days suggests the contract and the executing code are not generated from one source, and that a conformance check between them would catch this whole class before a caller does. BG-9 in particular is checkable by machine: render the transform, apply the published formula to the operands beside it, compare.

Findings

BG-1Blocking

The apply schema requires a key its validator rejects

apply_strategy_plan publishes request: { plan, planToken, confirm } with all three required. Sending exactly that is refused. No accompanying "missing key" error appears, which pins the validator's accepted set to exactly {confirm, planToken}.

Schema declares
required: ["plan", "planToken", "confirm"]
Validator returns
unrecognized_keys: ['plan'] at path: ['request']
Workaround — verified three times

Omit plan entirely. The post-state is already sealed in the signed token as postStateDigest, so the client copy is redundant on the wire. 

apply_strategy_plan({ request: { confirm: true, planToken: "<verbatim>" } })

Confirmed on the REPORT axis, on CONDITIONS/MARKET_READ, and on a from-scratch CREATE. Not a quirk of one code path.

Suggested fix: the schema is the stale half — it still describes a projection the server no longer consumes. Either drop plan from the published schema, or accept and ignore it. Right now the documented call is the one that fails.

BG-2Silent

Two zone columns cannot carry a condition at all

All five classifyZone columns declare the same conditionVocabulary. Two of them never emit any of it. Measured across 12 coins:

conditionVocabulary declares
ADX_zone overbought | oversold | neutral MFI14_zone overbought | oversold | neutral
Column actually emits
ADX_zone trending | developing | weak MFI14_zone bearish | bullish in vocabulary: 0 of 12

So ADX_zone is "neutral" — written from the vocabulary the platform publishes, using the operator it lists — reads FALSE forever. Not an error. Not UNRESOLVED, which would at least signal a missing input. It looks like a working condition that happens never to fire.

And the obvious repair is refused:

CONDITION_LITERAL_UNSUPPORTED
'trending' is not a value 'ADX_zone' can take — its vocabulary is
overbought | oversold | neutral.   Nearest canonical key: 'oversold'
No workaround for the column

Both directions are closed: every label that would fire is rejected at validation, every label accepted reads FALSE. ADX_zone and MFI14_zone are display-only — renderable for an agent to read, impossible to condition on.

Replacement — reproduces the zone exactly
ADX_zone   is "weak"      →  ADX    lt  20
ADX_zone   is "trending"  →  ADX    gte 25
MFI14_zone is "bearish"   →  MFI14  lt  50
MFI14_zone is "bullish"   →  MFI14  gte 50

Verified on BTC / SOL / XRP — three for three on both columns. Those cutoffs are consistent with observation, not extracted: the zone thresholds are published nowhere.

Suggested fix: the two columns look like they were wired to a different classifier than the one their contract describes — ADX to a trend-strength bucket and MFI14 to a directional one, while both still advertise the oscillator vocabulary RSI14_zone uses correctly. Publishing the real labels would make both usable immediately. Publishing the threshold values too would remove the guesswork above.

BG-3Blocking

Crowd ranks compile cleanly and never render

Every crowd metric declares transforms: ["rank", "value"]. get_strategy_column_contract returns a complete contract for the rank — header, formula, glossary, null behaviour. Then every render fails.

Compile returns
header: crowdAcc_rank_hi formula: ordinal(crowdAcc among the ranked universe, by ordering)
Render returns
INTERNAL_ERROR Internal server error

Ruled out, each with a live probe:

  • Not the single-coin case — fails identically at 1 coin and at 10.
  • Not null data — every coin in the 10-coin set had complete crowd values.
  • Not ordering — hi and lo both fail.
  • Not a subset — all 8 crowd rank shapes fail, settled and _LIVE alike.

The contract text points at the cause. Crowd ranks are the only ones documented as "ordinal across THIS REPORT's coins … computed per request"; every other rank reads the tracked universe. That per-request path is what breaks.

Replacement

Use CROWD_* × value and threshold it. Crowd metrics are already cross-coin-comparable percentages, so unlike VOLUME they need no normalising — ranking adds nothing a threshold cannot express. 

crowdAcc between 60 and 100
  →  UP on SOL (88.9) and XRP (100.0), NEITHER on BTC (40.0)

Suggested fix: either repair the per-request ranking path, or drop rank from the crowd metrics' declared transforms so the authoring surface stops offering 8 shapes that cannot be delivered.

BG-4Friction

Trajectory direction is computed on values the table hides

A trajectory column emits its slots at the metric's display precision, but _trend is derived from the unrounded series. The two can disagree, and the table gives no way to tell. DOGE at 1h:

Slots imply
RSI14_t2 38.3 RSI14_now 38.3 → flat
Column reports
RSI14_trend falling

The platform is right — RSI displays at precision: 1 and the true endpoints differ below it. But a reader reconciling the row sees a contradiction, and anyone recomputing a direction from the rendered slots gets it wrong at exactly the close calls that matter.

Workaround

Read _trend directly; never reconstruct a direction from the slots. Worth stating in the column's own meaning text, since the trap is invisible from the output.

BG-5Friction

INTERNAL_ERROR covers transient states and real faults alike

The same opaque error is returned for a genuinely impossible shape (BG-3, which never succeeds) and for a transient condition that clears on its own. That ambiguity cost about seven hours.

The correct apply shape was found at 18:00 and refused four times with INTERNAL_ERROR. It succeeded unchanged at 19:07. The 18:40 and 19:06 requests were byte-identical — same operation, same expectedRevision, same coins, same columns — and both tokens were seconds old. Nothing client-side differed.

Separately, the connector returned 503 on every endpoint for several minutes, and two CREATE applies timed out before the third succeeded.

Workaround

On INTERNAL_ERROR, change nothing and resend the identical request. On an ambiguous timeout during CREATE, do not retry blind — the strategyId is pre-allocated inside the signed token, so reading that id settles what happened before a retry can duplicate.

Suggested fix: distinguish retryable from terminal. A typed UNAVAILABLE or RETRY_LATER would have collapsed those seven hours to one retry, and would separate BG-3 — which is permanent — from noise.

BG-6Silent

A null column value reads FALSE, never UNRESOLVED

The condition engine documents three outcomes, and its own boilerplate is explicit about what the third one means:

“TRUE / FALSE / UNRESOLVED are three distinct states; UNRESOLVED means an input was missing, not that the read was false.”

Null column data does not reach that third state. crowdAccLive rendered —, and crowdAccLive gt 50 returned FALSE, with the evidence line carrying operand: "—". unresolvedCount stayed at 0 throughout. The connective table that follows is plain two-valued logic:

expressionmembersresult
ALLTRUE, nullFALSE
ANYTRUE, nullTRUE
ANYFALSE, nullFALSE
NOTnullTRUE
N_OF n=1TRUE, FALSE, nullTRUE, unresolvedCount: 0

The cost is that “not measured” is indistinguishable from “measured and false”. crowdAccLive is null whenever no concurrent sessions are running, which is most of the time — so a condition on it reads FALSE almost always, and reads it for the wrong reason. NOT is the sharp edge: NOT(null) returns TRUE, so a negated guard fires precisely when there is no data to justify it.

Workaround

Pair any condition on a nullable column with an ALL guard on a column that is never null, so the absence of data cannot be read as a positive. Never put a nullable column under NOT.

Suggested fix: route null operands to UNRESOLVED and count them in unresolvedCount — which is what the boilerplate already promises. If two-valued logic is the intended behaviour, the boilerplate should say so, because an author reading it today will design around a state that never occurs.

BG-7Silent

includeHigherTimeframe feeds no htf_* signal

All 25 platform sections were probed individually with derive_strategy_rule_view. Seventeen feed exactly one signal module each; eight feed nothing. The mapping is otherwise perfectly regular — but one of the eight is named for the thing it does not do.

reporthtf_rsi_oversold
includeHigherTimeframe aloneNOT_IN_REPORT
includeRsi aloneIN_REPORT, reportDefaultAllocation: 1

The six rung signals — htf_rsi_*, htf_ma_*, htf_trend_adx_* — arrive with the base modules. A single RSI14 column at rel: anchor, with no regime column anywhere in the report, puts htf_rsi_oversold and ltf_rsi_oversold in report. So the section that names the higher timeframe is the one section that cannot deliver it.

An author who wants higher-timeframe confirmation reaches for the obviously-named section, allocates 3 to htf_rsi_oversold, and has weighted a signal that never fires. Nothing in the response says so: NOT_IN_REPORT is reported without a cause and without a remedy.

Workaround

Enable the base section — includeRsi, includeMovingAverages, includeTrendStrength — or add one of its metrics as a column. The rung variants come free either way.

Suggested fix: have derive_strategy_rule_view return, for every NOT_IN_REPORT rule, the sections and metrics that would feed it. The server already knows the mapping — it is what produced these 25 answers. Returning it would close this finding and remove the need for any caller to rebuild the map by probing.

BG-8Silent

Colliding headers render, and both lose conditionability

offset is not part of a column's header name, so any two columns differing only by offset collide. Both still render:

coin…close_trendSMA20SMA20
BTC…rising$78,215.50$78,469.20

Two columns, two different and individually correct values, one name. And conditionColumns for that section returned seven outputs — close_t5 through close_trend. Neither SMA20 appears in it.

The control rules out the metric: SMA20 on its own appears in conditionColumns normally, with lt/lte/gte/gt/between. The collision is what removes it.

The cost compounds with BG-6. The table looks correct and an agent reading it as text sees both numbers, but a condition referencing SMA20 has nothing to bind to — and a null read is FALSE, never UNRESOLVED. The gate fails silently and reads as a genuine negative.

Workaround

Never place two columns in one section whose headers would match. The header is predictable from the column spec, so this is checkable before submitting.

Suggested fix: disambiguate the header when offset is set — trajectory already does exactly this with its _t3 suffixes — or refuse the section with a typed REPORT_COLUMN_HEADER_COLLISION. Rendering a column that cannot be referenced is the worst of the three available behaviours.

BG-9Silent

nearestZoneDist's published formula has the wrong sign

The transform catalogue states:

output = ((price − midpoint(nearest zone)) / midpoint(nearest zone)) × 100

The engine computes ((midpoint − price) / price) × 100.

coinsupport zonemidpointclosestated formularendered
BTC77,859–77,92377,89178,883+1.3%−1.2%
DOGE0.0854–0.09020.08780.0905+3.1%−2.7%
SOL92.12–92.9392.525100.57+8.7%−7.9%

Every coin renders negative where the published formula is positive. The denominator differs too, and SOL separates the two candidates: a midpoint denominator predicts −8.7% against a rendered −7.9%, while a price denominator predicts −8.0%. Solving ((mid − px)/px) for the price the engine used gives 78,837 / 0.0902 / 100.46 against close columns of 78,883 / 0.0905 / 100.57 — within 0.3%, consistent with the zone being read at the regime timeframe while close is the anchor's forming bar.

The header prose is correct — “signed % from price to the nearest support zone midpoint” describes what the engine does. Only the machine-readable formula disagrees, which makes this the worst kind of documentation bug: the two descriptions of the same field contradict each other, and the wrong one is the one a tool would parse.

Workaround

Build from the prose. Read the value as negative when price sits above support, and invert any threshold derived from the published formula.

Suggested fix: correct the catalogue entry to ((midpoint − price) / price) × 100. Worth checking the other sixteen entries the same way — this one was only caught by rendering the operands beside the result and doing the arithmetic.

BG-10Silent

Rung-scoped rank is described two ways in the same response

ATR_PCT ranked at rel: lower, anchor and regime, with an explicit two-coin selection. For the same header, the section preamble and conditionColumns disagree:

preamble, atrPct_ltf_rank_hi: “ordinal across THIS REPORT’S coins … rendered as rank/report-size; computed per request, so it reflects the coins in this report and not the wider market”
conditionColumns, same header: “ordinal across the tracked universe … rank/universe-size; the standing as of the last close, unchanged until the next one”
coin_ltf_rank_hi_rank_hi_htf_rank_hi
BTC47/7844/7848/78
SOL20/7824/7829/78

Report size is 2. Every denominator is 78. The values agree with conditionColumns and contradict the preamble. Only the anchor rung received preamble text that is correct for all three.

The preamble is what an agent reads as table context, so this is not cosmetic. An author sizing an _ltf rank threshold would take “top 3” to mean top 3 of the coins they selected. It is top 3 of 78 — so on a ten-coin selection that gate can match nothing at all, and nothing in the response says why.

Workaround

Trust the denominator you can see. The rank renders as n/78, so the scope is readable off the value even when the prose above the table says otherwise.

Suggested fix: make the preamble match conditionColumns and the values. If report-scoped ranking is intended future behaviour for the rungs, it is not what ships today, and the preamble should not describe it as though it were.

BG-11Blocking

ROC12 renders a raw fraction while its label says percent

The column meaning reads “rate of change vs 12 bars ago (%)”. The value is the raw ratio — a hundred times smaller. Measured with the 12-bar reference visible in the same table:

coinclose, 12 bars agoclose nowas a fractionas a percentrendered
HYPE79.7679.91+0.00188+0.19%+0.00%
ZEC836.45843.69+0.00866+0.87%+0.01%
BTC79,75578,967−0.00988−0.99%−0.01%

HYPE also rules out the obvious alternative — that the lookback is longer than 12. Its 15-bar change is +2.50%, nothing like the rendered +0.00%.

This is filed as blocking rather than silent because it breaks every numeric threshold on the metric. ROC gt 2 meaning “up 2 percent” must be written ROC gt 0.02. And because the value is small rather than absent, the gate never errors — it simply never fires, or always fires, depending on direction. rel_roc_positive and rel_roc_negative read this metric.

It is not a house convention. PPO sits in the same module, in the same rendered table, and is a percent — recomputed at −0.2477 against a rendered −0.25. ROC12 is the odd one out, which is what makes this a bug rather than a documentation preference.

Workaround

Divide any percent-denominated threshold by 100 before writing it against ROC. Or avoid the metric for gating and use CHG_*, which is percent-denominated as labelled.

Suggested fix: multiply ROC12 by 100 to match its label. Given PPO's behaviour beside it, that is almost certainly what was intended. Worth sweeping the other percent-labelled metrics the same way — this was found by rendering the operands next to the result, which nothing about the value alone would have prompted.

BG-12Silent

Three columns render a value that no condition can reference

These return conditionOperators: [] — not a numeric set, not is/in, nothing:

columnrenderswhat it is the natural guard for
SETTLED_AT2026-07-24the age of the whole CROWD_* block
nearestZoneRange$77,859.00–$77,923.00whether price is inside the zone
picksSpread_sessiondistinct coins picked / availablehow concentrated the field is

This is one class, not three unrelated bugs, and the cost is the same each time: the data is shown and cannot be used. An agent reading the table as text sees all three. The deterministic layer cannot reach any of them.

SETTLED_AT is the sharpest case. It is the only column carrying how old the crowd numbers are — measured at 32 days on 2026-08-25 — so there is no way to write a gate that refuses stale crowd data. Combined with BG-6, a crowdAcc gte 60 condition answers confidently from month-old evidence and nothing in the response says so.

nearestZoneRange is the same shape: the zone's bounds are rendered and unreachable, so “price is inside the support zone” cannot be expressed. Only nearestZoneDist is gateable, and that is a distance to the midpoint.

Workaround

None. The values can be read by the agent as narrative context, but no condition can bind to them. Treat anything they would have guarded as ungated.

Suggested fix: give each column operators, or expose a derived scalar carrying the same information. STRUCT_ZONES already does the second thing — nearestZoneAge is a gateable number derived from a timestamp — which proves the pattern is available and just was not applied here. SETTLED_AT wants exactly that treatment.

BG-13Silent

offset is accepted, spends budget, and is then ignored

offset walks a column back N bars. It works — on numbers. On a categorical candle-backed metric it validates, it consumes offset of the 32-bar columnLookback budget, and the column answers for now anyway. Nothing errors and nothing warns.

honours offsetignores it
close, ADX, swingHi, swingLo, STOCH_K, MFI14, pctB MA_ALIGN, BB_TOUCH, EMA_CROSS, PRICE_ZONE, BAR_FORMING

Measured across 78 coins at a 4h anchor, offset 0 against offset 8. PRICE_ZONE was identical on 78 of 78 — which on its own proves nothing, because a label can simply be stable. What proves it is that the metric's own inputs moved in the same render:

AMD @ 4hcloseswingLoswingHipositionzone
offset 0$480.70$451.62$482.3394.7%near high
offset 8$460.95$451.62$477.9435.4%near high ←

At 35% of its own swing range the honest answer is not “near high”. It is the offset-0 answer. EWY repeats it: 23% of range, still “near high”. So this is not a metric without history — the history is right there in the adjacent columns, and the classifier is not reading it.

Workaround

Read the numeric inputs at the offset and classify them yourself. close, swingHi and swingLo at offset N are all correct, and PRICE_ZONE's rule is known — percentage distance to the nearer swing. There is no workaround for reading a past classification directly.

Suggested fix: either honour offset in the classifiers, or reject it on these metrics. Silently accepting a parameter, charging budget for it, and ignoring it is the worst of the three options — a rejection would have taken one render to discover instead of a controlled experiment across 78 coins.

Closure, 2026-08-28: BAR_FORMING, the one candle-categorical left untested above, was measured at a 1h anchor on BTC/ETH/SOL, offset 0 against offset 8, with close as the moving control. The control moved on all three coins; the flag answered “forming” in both sections — including for a bar eight hours in the past, which is closed by construction and whose settled close prints in the same row. All five candle-categoricals now measured; every one ignores offset.

BG-14Blocking

The plan's documented byte cap is enforced against the compile's own preview

compile_strategy_plan's description says: “The serialized plan is capped at 256,000 UTF-8 bytes; a plan over the cap is refused with a typed error naming the cap and the measured size.” A 12,210-byte CREATE plan — twenty times under that cap — was refused with:

response
VALIDATION_ERROR: Strategy report preview mcp_result_bytes limit exceeded: 395404 > 256000.

The 395,404 bytes are not the plan's — they are the compile's own live report review, rendered across the request's coinSelection (ranked, ALL, limit 30: two custom sections, eleven columns, seven conditions, thirty coins). The description calls that review “bounded”; when its render exceeds the budget it does not bound itself, it refuses the whole compile. The practical consequence is unpublished anywhere: coinSelection is an authoring budget input — preview cost scales with limit × report width, and a plan that is legal, in budget, and far under the documented cap can still be uncompilable.

Reproduction: one CREATE compile of an omega.generate plan (trend-continuation preset), 2026-08-28 — the request and verbatim response are in data/audit/compile_dry_run_2026-08-28.json.

Workaround — verified

Shrink the preview footprint. Confirmed later the same day: the identical plan with an explicit three-ticker selection — the only fields changed were coinSelection and its assumption string — compiled viable: true.

Boundary — measured 2026-08-28

The largest ranked selection that still compiles, for this same report shape, is limit 4 — an exact adjacent-pair bracket: ranked/ALL/4 compiled viable (resolving to BTC, ETH, SOL, HYPE) while ranked/ALL/5 refused at 258,883 bytes; ranked/CRYPTO/4 also compiled. The byte curve is concave, not linear — 5 coins → 258,883; 19 → 368,235; 30 → 395,404 — so the first handful of coins spends most of the budget and no realistic ranked universe can compile at all. Boundary is report-relative (eleven custom columns here); a wider report refuses earlier. Record: data/audit/cap_boundary_2026-08-28.json.

Suggested fix: bound the bounded review — truncate or sample the preview instead of refusing the compile — or document the real enforcement point and its scaling so authors can budget for it.

What held up

A defect list is not a verdict on the product, so for balance: the authoring surface is in good shape. Everything below was exercised against the live compiler and passed.

Header contract Every legal column shape has now been rendered against the live compiler — 1,759 of 1,759 operand-expanded (301/301 structural) — and every rendered header matched its predicted name exactly. Zero mismatches across the 2026-08-24 and 2026-08-26 sweeps. The denominator is honest: 421 shapes the contract implied were removed as never-legal, not excused.
Condition grammar All 7 clause operators, all 4 group operators, conditionRef, a group referencing groups, required, and verdict resolution.
Provisional flag Correct throughout — true on every condition reading a custom column, false on the one reading an ambient header.
Legality model The engine correctly refused BB_PCT_B × classifyZone as non-composable, and named the allowed transforms in the error.
Write path All seven axes commit — IDENTITY, TIMEFRAME_PROFILE, REPORT, MARKET_READ, CONDITIONS, SETUP_GATES, LIFECYCLE.
Error quality Validation errors are genuinely good — they name the key, the allowed domain, and the nearest valid value. BG-5 is the exception, not the rule.
Indicator maths Checked against an independent source, not just for self-consistency. 60 BTC 1h bars diffed against the Hyperliquid public API: open, high and low identical on every bar, worst close gap 0.0126%. SMA20, EMA5, EMA13, RSI14 and ATR all reproduce to four decimal places from the textbook formulas.
Transform formulas 17 of 17 now verified, all exact — trajectory, efficiency, maxShare, aggregate, distance, spread, rank, value (including a non-zero offset), classifyZone, bandTouch, nearestZoneType, count, crossDetect, and the four zone transforms — the rendered support zone matched a real three-bar fair-value gap on the regime tape to the dollar, and its age counts from that bar's close. All 30 pre-computed indicator metrics reproduce too, including Bollinger, whose period (20) and multiplier (2.0, population sigma) are published nowhere and had to be searched for. The three metrics with competing conventions were pinned too: ADX uses Wilder smoothing, CCI uses mean absolute deviation, %K/%D is slow (14,3,3) — and in each case the rejected alternative misses by enough to flip a gate. rank is notably clean: hi + lo = universe + 1 on every coin tested.
Platform-native metrics The 32 metrics with no exchange equivalent were coherence-tested against BattleGrid's own numbers. CVD reconciles exactly — its per-bar delta equals BUY_VOLUME − SELL_VOLUME. SMART_RETAIL's rule was identified and holds 13 of 13. The structure zone matched a real three-bar fair-value gap to the dollar. This is a self-consistent system, not a black box.
Section membership Regular, not ad hoc. 17 of 25 platform sections feed exactly one module each, with no overlap, and every one delivers its module's full signal set — rung variants included. A section and its metric are interchangeable: includeRsi and one RSI14 column produce byte-identical membership.

How this was tested

Every column shape the metric contract declares legal was enumerated offline, batched under the measured sectionColumns cap, and rendered live — 15 batches, 300 shapes, one coin per batch for the header comparison and multi-coin renders for value checks. The condition grammar was exercised in a single report carrying every construct at once. Findings were then written to a sandbox strategy and read back to confirm persistence. Signal membership was measured separately on 2026-08-25: each of the 25 platform sections submitted alone to derive_strategy_rule_view and its IN_REPORT set recorded. The four sections in the final probe were measured jointly — membership is a union, so an empty union proves each member individually empty. Transform formulas were audited by rendering each transform beside its own trajectory slots in the same table, so no external data is needed and no sampling drift can enter between operand and result; where bars: "closed" was used the slots were additionally diffed against cached candles. Asset-class coverage was probed across STOCKS, TRADFI, INDICES and COMMODITIES — those tickers are perpetuals and carry funding and open interest, but every metric accumulated since the daily 00:00-UTC anchor (CVD, SPOT_CVD, OBV, VWAP) renders null on them, which combined with BG-6 makes a mixed-asset coin selection gate those columns silently wrong.

One incidental note for the budget model: columnLookback reported exactly 24 in all 13 renders — 1 through 30 columns, every transform, SMA200 included. It never moved, so it carries no information for a caller sizing a report. The cap that actually binds is sectionColumns.
