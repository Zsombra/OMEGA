The one-line characterisation

The system computes first-moment, ratio, ordinal and path statistics. It computes no second moment, no joint moment, and no transform. Almost every entry in both lists below follows from that sentence.

Supported
  • First moment — aggregate, the arithmetic mean
  • Ratio — spread, distance, within a unit class
  • Ordinal — rank, across coins
  • Path — efficiency, net move over distance travelled
  • Concentration — maxShare, max over sum
  • Sequence — trajectory, the last N values
  • Counting — N_OF, at layer 3
Absent
  • Second moment — no variance, no σ
  • Joint moment — no covariance, no ρ, no β
  • Regression — no least squares, no slope
  • Time-series percentile — rank is cross-sectional only
  • Transcendental — no log, exp, or power
  • Recursion — no cumulative sums, no exponential weighting
  • Higher moments — no skew, no kurtosis, no autocorrelation

The rule that gates everything: unit cliques

The second gating rule: only stored series can be chained

Unit cliques decide which pairs exist. A second rule decides which of those pairs can carry a stage-2 window operator, and it is just as sharp: a spread chains only when its base metric has a stored bar-indexed series.

The non-chaining ones are exactly the point-in-time reads. MARK, LAST and ORACLE are documented as “read live at report build time — not a bar close”; the SPOT_CLOSE_* are venue snapshots; CHG_* are published values; FUNDING_* and OI_CHG sample on their own schedule. No stored series means nothing for a window operator to consume.

This costs one construction I claimed earlier. Basis momentum — MARK spread SPOT_CLOSE_CB → trajectory — is not buildable as a single column, because MARK’s spread does not chain. The basis itself is fine; its evolution has to be read from the market-read text or across sections instead.

A narrower rule governs the chain to rank: only the moving-average family, the swing levels and VWAP can spread-then-rank — EMA5 EMA13 EMA20 SMA20 SMA50 SMA200 SWING_HIGH SWING_LOW VWAP.

What was measured, and what was not

A census is only worth having if it cannot quietly become false. Every buildable entry above is built and validated by the test suite, and every one was rendered against the live compiler. Three things about it were not measured that way, and saying so is part of the record.

Asset class — six families go silently null off-crypto

Non-crypto tickers on this platform ARE perpetuals. GOOGL, GOLD, SP500 and the rest all carry funding, open interest and a mark price. The prior assumption that they would lack them was wrong.

Every metric the platform describes as accumulated since the daily 00:00-UTC anchor renders NULL off-crypto: CVD, SPOT_CVD, OBV, VWAP. So do the venue spot closes (SPOT_CLOSE_CB / _BN) and the perp-spot state metrics. Every PER-BAR metric renders, including BUY_VOLUME, SELL_VOLUME, BUY_TRADES, SELL_TRADES, BUY_PRESSURE, VOLUME, RVOL, SWING_HIGH, REGIME_* and STRUCT_ZONES.

These families do not error off-crypto - they render an em-dash, and a null reads FALSE rather than UNRESOLVED (cookbook trap 11). A strategy whose coin selection mixes crypto and non-crypto gates them silently wrong, and the scorecard looks fully populated while it is not.

Gateability — rendering is not referencing

A column can render and still be unreferenceable. nearestZoneRange comes back with conditionOperators: [] - no operator at all. Categorical outputs carry only is/in, so they match a label but cannot be thresholded.

44 of 46 families are numerically gateable. 2 are label-only: crossover-event, oscillator-zone.

Attribution — the one field that is judgement, not measurement

The `attribution` field on each family is MY mapping of a construction to a paper, not a measurement and not the platform's claim. It says 'this column set implements the shape of that idea', which is a judgement call and is sometimes arguable - a rank of funding is the carry factor in perpetuals, but Koijen et al. did not write about perpetuals. Everything else in this file was measured against the live engine; this field alone was not. Treat it as a reading aid, not evidence.

Blocked how, exactly? Data vs operator

“Blocked” hides an important distinction. For nearly every entry above, the data is present and only the operator is missing. That is a very different situation from the data not existing, and it changes what you do about it.

Proof, from one render. Put a 12-slot return trajectory on an unbound section and the same column on a section bound to BTC. The platform prints two time-aligned return vectors:

 
SOL 0.48 -1.33 1.13 0.35 -0.42 -0.73 0.55 0.61 0.01 1.02 -0.01 0.46 BTC 0.89 -0.72 1.17 -0.57 -0.06 -0.39 0.22 -0.24 0.23 0.06 -0.31 0.04

From those two rows: σ(SOL) = 0.717, σ(BTC) = 0.557, cov = 0.256, ρ = 0.642, β = 0.827. Every one of those is “impossible” in the column layer, and every one is computable from data the platform already put on the page.

There is also a soft ceiling that is neither: the 32-bar lookback cap. A 12-period correlation is reachable; a 200-period one is not, because no column can see that far back.

Which layer needs the number?

This is the practical consequence, and it is the thing worth taking away.

For the agent to reason with
  • Ship the trajectory slots and let the model compute it.
  • ρ, β, σ, slope, percentile — all recoverable from rendered history.
  • Costs header width and tokens, nothing else.
For a deterministic gate
  • It must be a column — conditions read headers, not reasoning.
  • So Class-A statistics genuinely cannot gate anything.
  • Compute outside and bring the answer in as a threshold.

So the census’s blocked list is really a list of things the condition layer cannot decide on — not things the strategy cannot use. The platform’s own framing supports this: conditions are “deterministic reads … advisory: they may make you more selective, never less.” The reasoning was always meant to be the agent’s job. The column layer’s job is to put legible quantities in front of it — and a trajectory of returns is a perfectly legible quantity.

What this adds up to

This is a ratio-and-rank engine, not a statistics engine. It is unusually strong at the things a discretionary trader reads off a chart — how far is this from that, is the gap widening, which coin is most extended, how cleanly has price travelled — and it has no apparatus at all for the things a quant reads off a covariance matrix.

That is a coherent design rather than an oversight. Every supported operator returns something directly interpretable by a language model reading a table: a percentage, an ordinal, a label, a short sequence. Variance, β and spectral density are not things you glance at in a row of numbers and reason about — they need a model, and the model here is the agent, not the column.

The practical consequence. Anything named after a standard deviation, a correlation, or a regression must be computed outside and brought in as a threshold, or approximated. The nearest substitutes: efficiency for noise, spread → aggregate for standardisation, rank for relative extremity, and benchmark sections for dependence.
